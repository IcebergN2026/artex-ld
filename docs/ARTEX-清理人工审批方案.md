# ARTEX 清理人工审批方案

> 状态：设计稿，尚未实施。
> 对象：外网渗透场景中，自定义 `trace_cleaner` Agent 的清理计划、会话内人工审批和执行审计。

## 1. 背景与结论

当前 `trace_cleaner` 在发现特定漏洞后自动运行，并可通过 Godzilla MCP 执行删除。提示词虽然要求确认主机、文件归属和证据，但自定义 Agent 仍具有默认工具，且运行在 `ModeBypass` 下。提示词不是权限边界。

本方案采用以下结论：

1. 外网渗透场景的 `trace_cleaner` 不经过 `review` Agent，也不新增其他审核 Agent。
2. `trace_cleaner` 只读取证据并提交结构化清理计划，不能直接删除。
3. 人工审核直接发生在该自定义 Agent 的 ARTEX 会话界面，不在任务详情中再做一套审批操作。
4. 人只批准计划中列出的精确项目，不能在审批卡中改写路径。
5. 批准后由服务端执行器按已批准快照执行，不再让 LLM 自由生成删除命令。
6. 执行前重新验证，执行后确认结果；结果不明时不自动重试。

## 2. 人工审核显示位置

### 2.1 唯一操作入口：自定义 Agent 会话

位置：**ARTEX 对话页 → `trace_cleaner` 触发会话 → 清理审批卡**。

`trace_cleaner` 提交计划后，会话中先出现一条计划摘要消息，紧接着显示持久化的交互审批卡。审批卡是该清理计划的一部分，不是普通 Markdown 文本，服务重启或页面刷新后仍能恢复。

定位链接采用：

```text
/chat?c=<conversation_id>&cleanup=<plan_id>
```

打开链接时定位到对应会话及审批卡。全局审批记录和任务详情只提供状态、审计和跳转链接，**不提供第二套批准按钮**，避免不同界面重复裁决。

### 2.2 会话内审批卡布局

审批卡按以下顺序展示：

1. **标题与状态**：`痕迹清理审批 #ID`，显示待审批、部分批准、已拒绝、执行中、已完成或结果不明。
2. **目标**：任务、来源 finding、资产、主机标识、MCP 实例和 shell 标识；凭据只显示引用，不显示秘密。
3. **拟清理项目**：逐项复选框、精确路径、文件类型和来源 `[投放]` 记录。默认不选中，禁止“全选后不看内容直接批准”的快捷操作。
4. **证据**：每项可展开查看投放命令、原始输出和主机一致性验证；证据缺失的项目禁止选择。
5. **保留项目**：原 webshell、未登记文件、目录和其他持久化机制，明确标注“不在本次执行范围”。
6. **人工操作**：`批准所选项目`、`全部拒绝`、拒绝理由输入框。批准前再次显示目标主机和所选项目数。
7. **执行结果**：批准后原位显示执行前复验、实际动作、删除后验证、错误和审计时间。

人工只能选择已列出的项目，不能编辑路径或命令。需要修改时，拒绝计划并让 Agent 重新生成，确保批准内容与执行内容一致。

### 2.3 会话消息与服务端状态

- Agent 结束语只说明“已提交清理计划”，不能声称已经清理。
- 审批卡由后端计划状态驱动，不从会话文字解析状态。
- 人工裁决成功后，会话追加一条系统审计消息，记录批准/拒绝项目数、操作者和时间。
- 执行结果写回同一审批卡，并追加结果摘要，完整证据仍可展开。
- 审批卡不依赖仍在线的 Agent 会话；会话已结束也可由人审批，由服务端执行器处理。

## 3. 端到端流程

```text
finding 事件
  → trace_cleaner 自定义 Agent 只读规划会话
  → submit_cleanup_plan（结构化计划）
  → pending，会话显示人工审批卡，无任何删除调用
  → 人在该会话中逐项裁决（版本 CAS）
  → approved / rejected
  → 服务端执行器重新验证目标与范围
  → 逐项执行已批准且仍有效的项目
  → 删除后验证并写回结果
  → 原会话审批卡展示结果
```

约束：

- `pending` 阶段不得调用 `rm`、删除类 Bash 或其他等价写操作。
- `rejected` 是终态，不允许执行，也不自动重新提交同一计划。
- 同一任务、同一目标已有 `pending / approved / running` 计划时，新事件只关联现有计划，不重复生成。
- 服务重启不清空审批记录，不自动重试执行。
- `review`、`review_auto` 和任务级 `review_enabled` 均不参与此流程。

## 4. 数据模型

新增 `cleanup_plans`：

| 字段 | 用途 |
|---|---|
| `id` | 计划编号 |
| `task_id` | 所属任务 |
| `finding_id` | 来源漏洞，可为空但必须有明确任务和资产 |
| `asset_id` | 已确认资产；不能从摘要猜主机 |
| `target_key` | 服务端生成的稳定目标键，用于去重 |
| `source_conversation_id` | 来源自定义 Agent 会话，也是审批定位目标 |
| `mcp_server_id`、`shell_ref` | 执行端点的受控引用 |
| `target_snapshot` | 主机、shell 和验证结果快照，不含密码或令牌 |
| `status` | `pending/approved/rejected/running/succeeded/partial/failed/expired` |
| `version` | 乐观锁版本 |
| `decision_reason`、`decided_by`、`decided_at` | 人工裁决审计 |
| `expires_at` | 审批快照过期时间 |
| `created_at`、`started_at`、`finished_at` | 生命周期时间 |

新增 `cleanup_plan_items`：

| 字段 | 用途 |
|---|---|
| `id`、`plan_id` | 项目编号及所属计划 |
| `action` | v1 仅允许 `delete_file` |
| `path` | 不可编辑的精确路径，不是 glob 或 shell 命令 |
| `evidence_ref` | 对应 `[投放]` 活动或事实记录 |
| `decision` | `pending/approved/rejected`，只允许人工裁决写入 |
| `status` | `queued/running/succeeded/failed/unknown/skipped` |
| `before_snapshot`、`after_snapshot` | 执行前后验证结果 |
| `error`、`started_at`、`finished_at` | 单项执行审计 |

对 `(task_id, target_key)` 建部分唯一索引，仅约束活动状态计划，防止同一资产并发生成多个待执行计划。

所有项目在同一事务内一次性裁决；部分批准表示“批准部分项目”，不是跨请求持续修改计划。裁决后不能再次改变项目决定，需修改时重新生成计划。

任务、finding 或会话的历史展示不得依赖仍存在的凭据；快照只保留非敏感元数据。v1 由计划表保存人工裁决、项目表保存执行结果，不另建事件表。

## 5. 工具和执行边界

### 5.1 规划阶段

新增内部工具 `submit_cleanup_plan`，参数为结构化目标引用和项目数组，不接受任意命令。

`trace_cleaner` 规划会话使用代码级白名单：

- 任务图、节点详情、findings、证据读取。
- 经批准的只读 Godzilla 工具，例如 shell 列表、活性和文件元数据查询。
- `submit_cleanup_plan`。

规划阶段移除通用 `Bash`、文件写入和 Godzilla 删除/移动工具。不能仅依靠提示词写“禁止删除”。

### 5.2 服务端校验

提交计划时必须验证：

1. finding、task、asset、shell 的关联真实存在。
2. 目标属于原任务明确授权范围；网络可达不能代替授权。
3. 每个项目都有可读取的 `[投放]` 证据，路径与证据完全一致。
4. 不允许空路径、通配符、控制字符、shell 拼接、递归参数或额外命令；`path` 必须规范化，不能包含 `..` 路径段。
5. 普通 Unix 路径规范化后必须以 `/` 开头；远程 Windows 路径必须由专用 MCP 类型和验证器处理，不拿 Unix 规则拼接。v1 不支持 UNC、URI、通配路径或任意命令字符串。
6. 原 webshell、未登记文件和证据文件不能进入可批准集合。

v1 只清理已登记的普通文件。目录、注册表、服务、计划任务、持久化机制和批量递归删除不在本期范围。

### 5.3 批准后执行

执行器不使用 LLM 重新解释计划。每个项目执行前：

1. 检查计划仍为 `approved`，未过期，版本未变化，项目已获批准。
2. 重新读取 shell 和主机信息，与批准快照比较。
3. 再读一次投放证据和当前文件元数据；目标漂移则跳过并标记失败原因。
4. 通过 MCP 的结构化参数执行精确 `delete_file`，不得拼接 shell 命令。
5. 删除后独立查询，确认文件确实不存在，再登记 `[已清理]`。

删除超时、连接中断或结果无法确认时，项目状态为 `unknown`。不得盲目重试，因为第一次调用可能已经生效。

`running` 中发生进程重启时，未完成项目恢复为 `unknown`，由人工核对；不能自动重新执行。

## 6. 状态与并发规则

- 新计划：`pending`。
- 全部拒绝：`rejected`。
- 至少一项批准：`approved`；随后由执行器原子领取为 `running`。
- 全部批准项目成功：`succeeded`。
- 同时存在成功、失败、拒绝或结果不明：`partial`。
- 全部已批准项目执行失败：`failed`。
- 待审批超过固定 30 分钟：`expired`，不自动允许、不执行。v1 不新增用户配置项。

批准和拒绝请求携带 `expected_version`。数据库在同一事务内检查状态、版本和过期时间；并发重复裁决返回 `409`，前端刷新，不得重复执行。

执行器领取任务也必须使用数据库状态条件更新，保证同一计划最多一个执行者。

## 7. API 与会话集成

```text
GET  /api/cleanup/plans?status=&task_id=&conversation_id=&page=&size=
GET  /api/cleanup/plans/{id}
POST /api/cleanup/plans/{id}/decision
```

`decision` 请求示例：

```json
{
  "expected_version": 3,
  "items": [
    {"id": 101, "decision": "approved"},
    {"id": 102, "decision": "rejected"}
  ],
  "reason": "仅清理已确认的两个测试文件"
}
```

规则：

- 每个项目都必须有明确裁决，禁止漏项后默认批准。
- 全部拒绝时 `reason` 必填。
- 已终态、已过期或版本不一致返回 `409`。
- 详情接口返回计划、项目、目标快照、人工裁决和执行结果；列表接口不返回大字段。
- 会话页通过 `conversation_id` 读取属于该会话的计划；不能仅凭前端传入的会话 ID 越权读取其他任务计划。
- 当前系统只有单管理员，`decided_by` 记录当前 JWT subject `ARTEX`。本期不新增角色系统。

## 8. 触发器与提示词调整

审批功能上线前：

- `config-export/agent_triggers.jsonl` 中 `trace_cleaner.on_finding` 默认改为 `false`。
- 已有环境升级时不自动打开该触发器。

审批功能上线后，`trace_cleaner` 提示词改为：

1. 只收集证据和提交计划。
2. 计划提交后结束本轮执行，等待会话内人工审批。
3. 未收到服务端“计划已批准且可执行”的工具结果前，不得尝试删除。
4. 只有服务端返回删除后验证成功，才能写 `[已清理]`。
5. 被拒绝或目标漂移时停止，不绕过审批另找工具执行。

不修改 `review` Agent 提示词，不增加清理预审提示词。

## 9. 测试与验收

至少覆盖：

1. 自动触发只生成计划和会话审批卡，删除工具调用次数为 0。
2. 页面刷新、服务重启、Agent 会话结束后，审批卡仍恢复原状态。
3. 默认不选项目；无证据项目不可选择；未选择项目不能批准。
4. 全部拒绝、部分批准、重复批准和并发批准。
5. 未批准项目、后加项目、修改路径均不能执行。
6. 同一资产的重复 finding 不生成多个活动计划。
7. shell 变化、主机变化、证据消失、计划过期时禁止执行。
8. 原 webshell、未登记文件和任意目录始终不可进入执行集合。
9. 删除成功但验证失败时不能写 `[已清理]`。
10. 删除超时或服务重启后不自动重试，状态为 `unknown`。
11. 未认证请求为 `401`，跨任务和跨会话读取、裁决失败。
12. 在真实浏览器中验证会话定位、逐项选择、证据展开、人工裁决、状态恢复和执行结果。
13. 全局记录和任务详情只能跳转，不能产生第二次裁决。

上线验收标准：**人工在自定义 Agent 会话中批准前，以及目标发生漂移时，没有任何可达的删除路径；批准后也只能执行已批准快照中的精确项目。**

## 10. 实施顺序

1. 保持自动清理触发器关闭，避免继续暴露现有风险。
2. 先落数据库、只读 API 和会话内审批卡，不产生执行能力。
3. 收紧规划 Agent 工具，接入 `submit_cleanup_plan`。
4. 实现服务端执行器、复验、结果不明处理和审计。
5. 完成并发、重启和真实浏览器测试后，再由管理员手动开启 finding 触发。
