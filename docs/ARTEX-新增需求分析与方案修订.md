# ARTEX 新增需求分析与方案修订

> 状态：分析稿，尚未实施。
> 来源：`asset-tree-layout-requirements.md`、`pentest-topology-requirements.md` 及 2026-10-27 的补充要求。

## 1. 本轮结论

1. 修改位置是资产页内部的显示列表，不是发现页。资产页增加“宿主”视图，以六列表格聚合企业、域名、IP 和应用服务；原有资产类型视图保留。
2. 内网渗透拓扑进入任务详情。节点面板先显示结构化 JSON 和证据引用，不展示原始命令、HTTP 请求或响应；操作进度和后续利用流程不属于本期拓扑。
3. `trace_cleaner` 不进入审核体系，不增加任何审批入口；它在现有自定义 Agent 聊天框中列出清理清单，等待人工回复“同意”后再执行。
4. 本轮只修订文档和静态 HTML 原型。实施时每个功能点分别填写独立实施记录。

## 2. 资产页宿主列表

### 2.1 现有实现与差距

当前页面是 `web/src/app/(main)/function/assets/page.tsx`，使用企业、主域名、IP、子域名、应用、服务、接口七个独立 Tab。数据来自 `api.assets`、`api.searchAssets` 和 `api.assetCounts`，已有企业筛选、DSL 搜索、分页、刷新和删除。

IP 行虽有绑定域名，但不能把多个子域名及同宿主应用服务完整聚合；域名行也不能稳定表达“一个 IP 对应多个子域名”。因此需要新增统一宿主投影，不是修改发现页，也不是把 `db/finding_assets.go` 的发现树直接平铺。

### 2.2 宿主行模型

保留现有七类资产视图，新增“宿主”Tab 和只读宿主行投影。建议增加 `GET /api/assets/hosts`，复用现有认证、企业范围、搜索和分页参数，返回以下字段：

| 字段 | 含义 |
|---|---|
| `row_key` | 稳定宿主行键，如 `h:<ip>`；无 IP 时使用稳定资产键 |
| `company_id/company_name` | 企业名称，沿用现有公司关联 |
| `root_domain` | 主域名；裸 IP 无关联域名时为空 |
| `primary_subdomain` | 行内主要子域名，无则空 |
| `other_subdomains` | 其余子域名，折叠展示并可展开 |
| `ip` | 宿主 IP；域名尚未解析到 IP 时为空 |
| `asset_ids` | 该行包含的全部资产 ID，供行筛选、详情和定位使用 |
| `summary` | 聚合后的应用、服务、端点分类和数量 |
| `finding_count` | 当前筛选条件下的发现数 |
| `total_finding_count` | 不受当前筛选影响的行总数，仅用于稳定排序 |

行生成规则：

1. 有 IP 的域名资产与对应 IP 宿主聚合，不能为每个子域名单独生成 IP 行。
2. 多子域名行只显示一个主要子域名，其余显示“另有 N 个”，展开后仍可逐个定位。
3. 主要子域名按全局直接发现数降序、名称升序确定；筛选不改变主要子域名选择，避免行内容跳动。
4. 裸 IP 行保留 IP，`root_domain` 和子域名字段留空。
5. 应用、服务、端点按当前宿主行实际包含的资产去重汇总，不能把其他宿主的发现合并进来。
6. 无关联域名、无 IP 的域名资产仍保留一行，不能因缺字段被过滤掉。

### 2.3 排序解释

“按发现数排序”与“排序不随筛选结果跳动”存在潜在冲突。本方案采用以下可验证解释：

- 企业和行顺序使用未筛选的全局 `total_finding_count`。
- 单元格显示当前筛选后的 `finding_count`。
- 并列时按企业名称、IP/主域名的稳定键排序。
- 分页在排序后的完整宿主行集合上执行。

这能保持筛选前后行位置稳定。如果产品实际希望按筛选后的数量重新排序，需要明确选择，并放弃“顺序不随筛选变化”。

### 2.4 页面布局与交互

入口固定为 **资产 → 宿主**，不新增发现页面：

```text
企业 | 主域名 | 子域名 | IP | 应用服务接口 | 发现数
```

- 宿主表占满整行，下面才是同一资产页内的发现列表；不弹出独立发现抽屉。
- 企业分组连续显示，同组后续行隐藏重复企业名；裸 IP 的主域名和子域名留空。
- 应用、服务、接口合并在同一单元格，默认显示少量条目，其余用“还有 N 个”展开或悬停查看。
- 点击整行筛选下方发现列表，再点同一行取消；面包屑提供“返回全部资产”。
- 行筛选通过 `asset_ids` 或专用宿主 scope 过滤，必须包含该行全部子域名和关联资产。
- 保留现有企业筛选、DSL 搜索、刷新和分页。任务、状态、严重度只过滤发现列表，不改变宿主行的稳定顺序。
- 窄屏横向滚动，不把六列压成卡片；特别长的名称才省略并提供悬停全文。

### 2.5 验收

- 两个子域名解析到同一 IP 时只有一行，且另一个子域名可展开。
- 裸 IP 行的域名列为空，应用和发现数正确。
- 点击多资产行后，列表包含该行全部资产的发现，不漏掉非主要子域名。
- 应用筛选、分页、面包屑和返回操作组合使用不丢失状态。
- 1280px 和窄屏下均可访问六列；长企业名不挤占其他列。
- 多页、同名资产、无 IP 域名和零当前发现数场景有稳定结果。

## 3. 任务详情内网渗透拓扑

### 3.1 展示位置

在任务详情增加“内网渗透拓扑”页签，与现有节点、发现、复测和审批分开。拓扑只使用当前任务图及其授权资产。

采用 `Graph Core + Layered Direction + 节点面板`，使用项目现有 `@xyflow/react`。一期提供：

- 入口向左、内网向右的层次布局。
- 缩放、适配视图、小地图和图例。
- 节点详情抽屉和关系编辑。
- 大数据量时再评估 canvas 渲染，不提前引入第二套图实现。

### 3.2 节点规则

1. 一个内网 IP 一个节点；同一 IP 的不同服务、URL 和端口合并到该节点。
2. 不合并不同 IP，也不按主机名、MAC 地址或推测身份合并。
3. 外网只显示疑似或已确认入口。普通外网资产、仅扫描过的资产和未发现入口关系的资产不显示。
4. 内网节点必须属于至少一个入口，或有指向它的横向关系；禁止游离节点。
5. 一个内网 IP 可从多个入口或上游到达时仍只保留一个节点，指定一个主入口，其余关系作为额外边。
6. 节点显示 IP、已知主机名、入口状态和备注标记；主机名未知时留空或显示未知。不显示未测试/已测试、执行中、扫描完成等操作状态。

入口判定：

- finding 类型为 getshell、RCE、文件上传或反序列化，且严重度为高危或严重，自动标为“疑似入口”。
- 自动规则不能直接产生“已确认”。
- 只有人工确认后才显示为“已确认入口”，记录确认人、时间和证据。
- 撤销确认后回到疑似；不再满足展示条件时从图中移除，但保留审计数据。

### 3.3 关系规则

| 类型 | 含义 | 样式 |
|---|---|---|
| `entry` | 外网入口到内网 IP 的首次发现/立足关系 | 实线，有证据 |
| `lateral` | 已确认内网 IP 到另一内网 IP 的横向关系 | 与入口边区分的虚线，有证据 |
| `unknown` | 已知内网 IP 属于某入口，但取得方式尚无证据 | 入口虚线，标注“发现方式待确认” |

未知关系是显式的待补全状态，不伪造证据：

- `evidence_ref` 可为空，`source=system_unknown`。
- 后续发现真实证据时更新原关系，不新增重复边。
- 人工可修改关系类型、指定证据或删除错误关系；修改留痕。
- “从入口发现”与“凭据复用”只是 `entry/lateral` 边上的证据说明，不增加第四类边。
- 布局按主入口的最短层次排列，额外横向边不能把一个 IP 复制成多个节点。

### 3.4 节点面板：结构化 JSON 优先

打开节点的展示顺序固定为：

1. **节点 JSON**：直接显示 `ip`、`hostname`、`os`、`ports`、`account`、关系及 `evidence_ref` 等结构化字段。
2. **机器信息**：IP、主机名、操作系统、开放端口、当前账号、权限级别和最后活动时间；未知值显示“未知”，不推测。
3. **关系管理**：新增、编辑、删除关系并保留审计历史。
4. **人工备注与历史**：备注内容、编辑人和时间，历史版本可查看。

不显示原始命令、命令输出、HTTP 请求或响应。JSON 仅保留证据引用，需要排障时由现有证据详情功能另行查看，不在拓扑抽屉展开原始内容。

### 3.5 数据与接口方向

复用任务资产关系和人工备注，不维护第二份独立事实。需要补充：

- 入口状态、主入口及人工确认审计。
- 类型化边：`task_id/from_asset_id/to_asset_id/type/evidence_ref/source`。
- 备注历史：旧值、新值、编辑人和时间。
- 关系编辑审计；删除采用可追踪方式，不直接抹掉历史。

拓扑接口返回轻量节点和边；节点抽屉按需读取结构化 JSON 及机器详情，证据字段只返回引用。所有写入校验资产属于同一任务、边类型合法、证据存在，禁止跨任务引用。

## 4. 与旧拓扑方案的冲突处理

以本次 `pentest-topology-requirements.md` 为准，`pentest-topology-asset-progress-plan.md` 中以下内容不再作为本期验收标准：

| 旧方案 | 本次处理 |
|---|---|
| 无证据不画线 | 改为允许 `unknown` 虚线，明确“发现方式待确认” |
| 抽屉仅资产信息和备注 | 改为结构化 JSON 第一，再显示机器信息、关系和备注历史 |
| 机器名称、地址、区域、来源均可编辑 | 本期只开放关系和人工备注编辑，事实字段不随意改写 |
| 节点显示操作执行中和脉冲状态 | 移出拓扑；不显示操作运行状态 |
| 扫描、利用、凭据、会话操作进度 | 拆为独立后续需求，不与拓扑耦合 |
| 操作统计与进度联动 | 本期不实施，也不作为拓扑完成条件 |

旧方案中仍保留的内容：使用现有 React Flow、入口到内网的有向布局、节点抽屉、人工备注和轻量拓扑接口。

## 5. 痕迹清理对话确认方案的补充

最终流程为：

```text
finding 触发自定义 trace_cleaner
  → 在现有 /chat/ 会话列出测试文件、地址和清理方式
  → Agent 停止并等待
  → 人工在同一聊天框回复“同意”/“仅清理……”/“取消”
  → 只清理当前清单并回写结果
```

不设置审批卡、审批页、审批记录入口或任务审批页签；不让 `review` Agent、`ReviewRunner` 和 `review_auto` 参与。普通聊天界面之外仍需要最小服务端工具闸门，确保旧消息、工具输出和助手伪造的“同意”不会触发删除。

详见 `ARTEX-清理人工审批方案.md`。

## 6. 实施边界

本轮没有修改业务代码、数据库、Agent 提示词或线上配置。后续实施顺序建议：

1. 先完成 Dispatcher 模板引用修复和痕迹清理对话确认闸门。
2. 再实现资产宿主行投影与六列表格。
3. 最后实现拓扑及节点抽屉，避免把资产操作进度混入同一改动。

两个修复功能点分别使用：

- `ARTEX-清理人工审批-实施记录.md`。
- `ARTEX-漏洞派发模板引用修复-实施记录.md`。

新需求实施时同样各自建立独立记录，并进行后端、数据库、前端和真实浏览器验证。
